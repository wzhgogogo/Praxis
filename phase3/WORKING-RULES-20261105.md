# 3b 工作规则调整（2026-11-05，用户已同意）

依据：11-02 至 11-04 共 314 个提交，其中至少 178 个是冻结、记录、同步、合并类流程提交；D4、D8 连续多轮 Live 每次只暴露一层问题。复核者与 Argon 的复盘结论一致：方法错了，不是缺人手。

## 1. 一条链路，一个会话负责到底
- 同一条纵向链路上的卡点（例如 D4：找店 → 认店 → 查位 → 交接），由一个会话从诊断、修复、真实回放一直负责到 Live。
- 该会话可以直接修改调用方、测试和 fixture，不再跨会话申请“窄授权”。
- 三条底线：不放宽店铺身份判断，不放宽安全或 Guard 规则，不增加预算或时限。碰到这三类，停下，附数据报告，由用户决定。
- 只有真正不相干的工作（例如前端、测试优化线）才另开会话并行。

## 2. 证据标准
- 针对 Live 失败的修复，红灯必须来自真实录制（快照、HAR、时间线），写明路径。手写或构造的测试页只能作补充，不能单独作为验收。
- 验收标准：在真实回放上越过当初失败的那一步。“门禁全绿”只说明没有回归，不说明修好。
- 复核者先在真实录制上把整条链路查一遍再下结论；时间上限（导航、provider、候选、总时长）作为一整条链一起审。

## 3. 减少仪式
- 工作过程中只跑相关测试；只在合入 main 前和 Live 前各跑一次全套门禁。
- 冻结 SHA 只用于 Live 和留出集。
- 复核者不再逐个分支复跑全套门禁，改为抽查，重点核对真实录制上的证据。
- 合并提交尽量少，不为每个阶段单独提交“记录、冻结、封存”。

## 4. 共享文件
- docs/STATUS.md、DEVLOG、TEST-LOG 只在合入 main 时更新一次。
- 预算账本改为每个会话各写自己的文件，用脚本汇总；每一次真实调用仍必须先记账。

## 5. 不变的部分
- 留出集：原文承诺、冻结、不让 Codex 读取，全部照旧。
- 两级签收、组装门禁、S0 定义不变。
