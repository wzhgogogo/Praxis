## 承诺
固定 Tabelog 一批 → 未满足现有交付条件且预算允许时 TableCheck 一批 → 按原规则展示或记录未完成。一批沿用当前候选／查位上限；来源内沿用现有排序。来源切换找新原生候选，不重新跨站搜索上一站同一家店。每个原生候选仅进入所属平台查位。

冻结 Semantic Prompt、Schema、Compiler、Gold、时间人数解释、H001 涩谷地点要求及既有核验、条件强度、证据展示规则、原全局预算、取消和只读安全。不带入历史 mini-live 的 1km 或 3km。沿用最后成功的默认浏览器网络，不显式10808，不重查网络。
不开发智能择源、并行／反复切站、新地理／排序、多来源合池、完整实体合并、控件重构、matcher长尾、其他Case新能力。不commit/push。

## 执行规则
- Tabelog本批满足交付即实际展示，TableCheck零调用。
- 无位、UNKNOWN、条件不满足或结果不足，以及无候选／来源访问失败，记录原因；原剩余预算允许时转TableCheck。
- 单候选失败继续本批其他候选；用户取消、全局预算耗尽、现有系统级终止则停止，不启动第二来源。
- 两批结束不启动新Tabelog批次。若现规则仍不允许展示或正常无结果收尾，记录“本轮有界范围已结束、任务未完成”。不伪造全站耗尽，不降低数量或改写成功。

## 改动A：原生发现
复用已验证搜索解析接正式H001入口，候选保留真实平台、门店ID、详情入口、来源资料。仅必要来源进度：当前来源、本批处理状态、剩余候选和停止原因。不建策略引擎，不把抽样批次当全站。无Google餐厅ID不能单独拒绝；不伪造Google ID或来源证据，保留现有地点和条件核验。

## 改动B：共用matcher后段
每站提取现有后段：Google候选经跨源matcher，原生候选经同源门店确认，汇入同一查位代码。保持准确请求绑定→日期人数时间操作→实际状态确认→库存提取→原证据输出。
同源证明基于真实门店ID、详情页与预约入口关联；禁止native=true授予HIGH、复制同页电话自我匹配。后段不再全站搜索或Google对照，但保留当前页归属检查。仅提取接线，不同时改控件策略、完成判定或扩大超时。
matcher保留指定门店、跨源事实关联、明确同店换平台能力。来源内按既有门店ID去重；跨源复用可靠判断；疑似重复无法确认不合并事实库存，也不作为两个确认不同餐厅凑数量。不建设实体合并系统。

## 改动C：正式组合
原生观察经正常事件／接纳进入Runtime，后续调查、事实、展示和停止走现有正式Agent流程。执行层固定来源顺序，不新增平台选择模型动作，不按Case ID写产品特例。mini-live只保留启动限额产物，撤掉重复选店续查成功判断。
Evaluator复用现入口，核验地理条件同店请求库存。Google匹配不是唯一合法身份路径，也不能跳过原生关联。若Accepted ADR限定Google候选，新增证据路径决策说明，不静默改历史决策或用户需求评分。

## 三阶段与独立review
1. 提取两站后段且原入口调用，复用正常查位、明确无匹配时段、请求未确认、局部失败、预算、取消测试。只签收重构接线。
2. 实际Router/Runtime/Agent组合替换外部响应，原生候选从来源观察进入，不预填合格候选。三主场景：Tabelog可交付实际PRESENT_RESULTS且TableCheck零调用；Tabelog不可交付转TableCheck自己的候选、准确请求不变且实际展示；两站未完成如实停、任务未完成，不伪报全站无位或成功。复用或补齐串店、日期人数不一致、无证据无位、取消、切源预算不重置。模型调查展示部分须现有真实模型＋固定来源验证，脚本动作不足。运行前记录选定场景与既有上限，不跑其他Case，不以重复运行追求成功。
3. 前两阶段交主chat独立看diff／组合证据，有缺口修正复审；通过后才发继续指令执行唯一一次H001有界Live。用户已授权此Live，无需重复用户审批。正常物化当前H001日期、原条件预算，从发现计时含所有读取身份事实查位。未触发第二站记未覆盖。确定性缺陷回所属切片，不自动重跑完整Live，不用历史库存。

按INDEX及Planning/Test/Eval/Post-change最小充分验证，复用覆盖，不增框架兼容层机械测试。保留所有旧dirty，本轮前基线 /private/tmp/praxis-h001-native-start-20260929/ 保存HEAD diff、status、文件SHA256。历史成果不冒充本轮。
