## 1. 研究问题与边界

用户指出，人数控件只是杂乱网站中的一个局部问题；应先实际操作 TableCheck、Tabelog，再设计能处理整个流程的平台能力。本次据此调整研究单位：从单个控件改为“条件设置 → 查询生效 → 结果解释 → 商户页面 → 时段/套餐 → 提交前停止”。

本次使用用户 Chrome 的 CUA AX 树、截图与真实点击，新开研究标签页；没有运行 Praxis Browser Executor，也没有运行 Stagehand、browser-use、Midscene 的模型流程。复用了用户浏览器环境，因此站点缓存、语言、地图中心等不是受控的干净初始状态。输入为 2026-09-19、19:00、2 人；八芳的 17:00 是明确标注的替代时段探查。操作预算上限约 30 分钟 / 80 个 UI 动作，完成四家商户观察后停止，没有为了凑满预算继续探索。

不登录、不填个人资料、不接受商户确认、不选进入身份验证的套餐、不提交预约。没有采集网络日志，不能把“未点击提交”报告为经网络审计的零外部写请求。观察记录在本次任务的 CUA 工具结果中，下表是人工摘要，不是可直接 Replay 的原始 artifact；没有保存独立截图文件。研究新建的五个标签页已关闭，用户原有页面保持原状。

## 3. 跨页面的真实问题

### 3.1 页面结构不等于当前可操作界面

- TableCheck 日期弹层截图显示一个月份，AX 却包含约十二个月。日期名反复出现，需要月份和区域上下文。
- Tabelog 筛选弹层打开后，背景结果依然进入 AX；背景和弹层各有时间/人数控件，出现相同 ID `svt`、`svps`。仅按全页 ID 或文字定位会产生歧义。
- Tabelog 的 Specify、日历日期、Plan details 在 AX 中可表现为 text，而非标准 radio/button；真实点击能够触发交互。过窄的角色白名单会漏掉实际入口。

**设计需求：** 观察结果应保留活动弹层、区域、父子关系、可见性与控件状态，先确定操作范围再定位。不能只输出一长串扁平文字或按钮。

### 3.2 输入值、启用状态和查询生效是三个事实

- Tabelog More filters 初始显示日期、7PM、2 人，但 Unspecified 处于选中状态。填写的值并不自动代表已启用筛选。
- TableCheck 点击 9/19 后 AX 曾报告无变化，截图却显示日期高亮；随后查询摘要才确认条件生效。
- Sushi Sendou 与 141 提供了条件正常保留的对照，不能把所有跳转都当作重置。

**设计需求：** 分别记录“想查什么”“页面编辑值是什么”“当前结果实际针对什么”。读取新的结果摘要或商户页条件后，才能把结果绑定到请求；不能从调用参数直接生成已满足证据。

### 3.3 无变化可能是加载、新标签页或 AX 不完整

- 两家 TableCheck 商户都在新标签页继续；原页 AX 无变化并不表示点击失败。
- Tabelog 弹层/日历异步更新，需要后续观察才出现完整内容。
- 日期视觉选中状态可能未出现在 AX diff 中。

**设计需求：** 动作后检查同页状态、标签页变化和加载状态；观察有界等待和重新提交动作必须分开。不能“没看到变化就再点一次”，也不需要无限重试。

### 3.4 有结果不代表满足条件

- TableCheck 明确显示 No exact matches within your search area，下面是 Alternative suggestions，却包含多家 19:00 的时段链接。不能因为时间吻合就忽略地理范围不匹配。
- 八芳 19:00 disabled 而其他时间可选；这是目标时段不提供在线选择的证据，不是所有时间无位或网站不可访问。
- 八芳商户信息中的平均消费与实际套餐价不同；公开页同时展示三小时套餐，但注明仅 11:30–16:00，17:00 的选项页只见两个两小时套餐。

**设计需求：** 证据保留所在结果分组、日期时间、人数、商户、套餐、价格口径和限制；区分 exact、alternative、unknown，而不是只提取 AVAILABLE 布尔值。上述名称是设计语义，不是已新增 Schema。

### 3.5 同一平台存在多种流程和商户规则

- 141 是长表单：规则、日期人数、二维时段表、套餐、问题、个人信息混排；表格时段使用图标，必须保留行列对应关系。
- 141 人数原生选项本次只有 2–6；正文又写 9 人及以上电话联系、包间晚餐最低消费等限制。不能把看不到更大人数一律归因于控件坏了，也不能由这些文字猜测未显示的 7–8 人流程。
- 100 Spoons 则先显示规则确认页：繁忙时两小时、普通客人预约开放范围与会员不同、儿童椅有限等。未经过确认不能声称后续条件已核验。
- Tabelog 套餐页的 Select 导向邮件身份验证，而搜索结果时段链接也带 `/booking/`。按 URL 含 booking/reserve 一律拦截，会一起拦住公开查询路径。

**设计需求：** 根据页面阶段、动作含义和实际效果区分继续查询、接受条件、提供身份信息、最终提交；URL 仅是线索。保留 Policy/Authorization 权威，页面按钮文案不构成用户授权。此次不决定 Confirm and continue 是否可自动点击，后续需独立查明其效果。

## 4. 应如何重新组织解法

方向是建立完整的“观察 → 提议 → 受控操作 → 检查变化 → 接纳证据”闭环。三层职责足够，不先建设新的通用平台框架：

| 层 | 应解决什么 | 不应承担什么 |
|---|---|---|
| 通用 Browser 能力 | 有范围的 DOM/AX/视觉观察；当前目标定位；原生/自定义控件；弹层、标签页、异步变化；动作后验证与具体失败反馈 | 认定餐厅符合预算或库存已锁定 |
| 薄站点知识 | 平台常见入口、页面阶段、筛选启用方式、结果分组、跳转关系和停止点；允许多种页面变体 | 写死每家店的点击脚本；复制另一套长期自治 Agent 循环 |
| Restaurant + Runtime 现有职责 | 门店身份、请求版本、条件适用性、套餐/人数/时间/费用限制；证据接纳、授权及最终状态 | 根据模型的“操作成功”直接宣布可订或预约成功 |

薄站点知识可先通过现有 Adapter / Context 表达；是否做独立 skill 格式取决于真实重复维护成本。TableCheck 与 Tabelog 是两个真实站点消费者，但仍属于一个 Restaurant Domain，不能据此声称已证明跨 Domain 业务抽象。

## 5. 三个仓库怎样进入比较

此前“先修 combobox，再考虑框架”的实施优先级过窄。保留已核实的源码事实，**选型单位改为同一完整流程**：

- **Stagehand：** 验证有范围的 DOM/AX 观察和可审阅动作候选，能否减少活动区域、重复目标和导航处理代码；模型提议与实际执行仍隔离。扩展运行环境与现有部署兼容性尚未验证。
- **browser-use：** 重点对照 DOM/AX/布局序列化、会话和标签页管理、动作后状态处理。只有完整流程收益足以抵消 Python 接入成本，才考虑引入运行组件；不能只借下拉框一处实现便认为研究完成。
- **Midscene：** 用已经观察到的 AX 缺失状态、图标表格、非标准点击目标检验视觉定位价值。先研究定位/观察边界；截图可帮助找目标，但看见高亮不等于查询生效，更不等于任务完成。现有模型视觉能力及供应商决定仍需另行处理。

不同时接入三套循环。先让同一 Harness 使用同一任务、相同页面输入、相同停止规则与结果契约对照候选。源码研究与这次 CUA 成功都不证明任何一个库在目标部署中成功。

## 6. 下一切片的建议验收，待讨论后实施

用户入口：给定门店/区域、日期、时间、人数，完成预约前调查，返回可核对的选项、替代条件或明确未完成原因，并提供正确的继续入口。

最小验证面沿用本次两站四家店的真实失败机制，不写死其名称或库存：

1. 正常路径：输入启用、搜索摘要和商户套餐页条件一致；证据支持结果。
2. 替代路径：区域无精确结果、时间不可选时，保留原条件并明确区分替代建议。
3. 页面变化：弹层与背景同名控件、日期视觉状态、新标签页、异步加载不会导致重复点击或串页证据。
4. 限制与停止：套餐适用时段、最低消费、人数规则正确关联；到确认/身份/提交边界停下并说明缺少什么。

按既有 Test 矩阵，实施时先复用/扩展本地真实浏览器 Fixture 与生产组合集成，再检查独立 artifact 评价，最后有界 Live。此次走查内容已经被开发者看到，后续只能作为 development / regression 输入，不属于 Clean Holdout。未知框架收益用完整结果正确率、条件错配次数、正确停止、耗时、模型调用/token 和维护代码量测量；不以一次按钮成功或步骤越少越好决定胜负。
