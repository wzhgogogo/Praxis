# Project Praxis（知行）——市场、切入场景与可行性分析

> **Not just answers. Outcomes.**

基于 Copilot 4000万 WAU 的 prod 数据(2026-03-21) + Afterburner 竞品评测(N=770-1508,2026年4-5月) + UXR 用户访谈 + Copilot proactive 功能全景，为“碎片化生活任务管理”方向提供相邻需求、现有产品缺口和技术可行性的佐证，并用于选择第一个 Build 场景。

> **证据边界：** Local、Shopping 等类别占比较高，说明生活类需求具有足够大的相邻市场，但不能直接证明 Praxis 的产品方向成立，也不能替代真实用户 PMF 验证。

## 当前 Build 决策（2026-08-04）

Praxis（知行）确定从 **日本市场的 Local 场景**开始 Build。第一阶段聚焦具有跨平台、跨时间和持续跟进特征的外出事务，以聚会、餐厅、预约、交通和日程协调作为代表性任务。

选择日本 Local 不是因为某个需求占比可以直接推出产品成立，而是因为它同时具备明确的相邻需求、明显的多平台碎片化问题，以及可以通过 API、Deep Link、邮件/日历和用户确认渐进实现的技术路径。

正式决策和 Build 边界见：`2026-08-04-日本Local市场切入与Build决策.md`。

## 一、核心假设

**你要做的**:帮用户管理"重要但碎片化、需要持续跟进"的生活任务——不是一次性问答,是 ongoing、有状态、跨时间的任务管理。

**两个典型例子**:
- **购物**:不是"帮我搜个洗衣液",而是"快没了 → 哪个平台最便宜 → 上次买的牌子好不好 → 趁打折下单 → 跟踪发货"——一个任务跨好几天、涉及多个平台、需要记住偏好
- **保险理赔**:出了事 → 该找哪个保险(public knowledge) → 我的保单号/条款(private knowledge) → 流程是什么 → 准备材料 → 提交 → follow up → 一个理赔拖一个月,十几个碎片化 todo 全靠人脑记

**区分**:
- **Public knowledge** = "保险理赔一般怎么做"(流程、最佳实践、坑)
- **Private knowledge** = "你的保单是 XXX、你的偏好、你的消费习惯"
- 两者结合 = **personalized, proactive task management for real life**

### 2.3 这些场景现有 AI 做得好吗?——很差

Afterburner 竞品评测(真实用户用自己的 query,在 Copilot/ChatGPT/Gemini 上同时跑):

**Shopping(N=775)**:
- Copilot 输在:LP1(40%)没有图片/对比表;LP2 不主动预判下一步
- 用户要的:比价 → 看评价 → 了解发货/退货政策 → 下单——**是一个多步跟进流程,不是一次回答**

**Travel & Local(N=770)**:
- Copilot **24.6%** vs Gemini **40.9%** vs ChatGPT **34.5%**——最弱领域
- 62% loss 因为"只给信息没法行动"(纯文字,不能点/订/导航)
- 51% 没有地图/图片
- 用户场景:规划行程(40%)、探索吃喝玩(24%)、比价航班酒店(18%)、附近推荐(11%)

**核心:现有 AI 的回答质量已经不错了,但它们的根本问题不是"回答不好",是"不帮你跟进"。** 每次对话从零开始,不记得你上次比到哪,不会主动 follow up。

## 三、为什么 Copilot/ChatGPT 做不了你要做的

### 3.1 Win rate 口径说明

竞品评测测的是**单次回答质量**(用户看一轮对话结果选"哪个最好"),不是"能不能帮你持续跟进一个生活任务"。ChatGPT win rate 34% 说明**它单次回答确实不错**——但这不等于它能帮你管理 ongoing 的保险理赔或购物清单。

### 3.2 Copilot 做了很多 Proactive,但没有一个是"帮你跟进生活任务"

Copilot 的 proactive 功能全景:

**已上线的**:
| 功能 | 做什么 | 跟"生活任务跟进"相关吗 |
|---|---|---|
| Scheduled Tasks | 用户自己设定时器"每天/每周跑 task" | ❌ 用户告诉 AI 做什么,不是 AI 发现你该做什么 |
| Task Completion Notification | task 做完了 push 通知 | ❌ 事件通知,不是主动发起 |
| Suggested Tasks | 主页推荐 task 卡片 | ❌ 内容推荐,不是"你需要做这个" |
| Fresh Suggestions | trending 建议 | ❌ 内容新鲜感 |
| Conversation Actions | 回答里嵌跟进链接 | ❌ 对话深度引导 |
| Discover Feed | 个性化 feed | ❌ 内容消费 |
| In-App Notification Framework | GA,各场景可发通知 | 基础设施 ready,但没用来做生活提醒 |

**在实验中的(效果不好)**:
| 功能 | 做什么 | 结果 |
|---|---|---|
| Topic Continuation | 从对话历史提取"还没完的话题"→ 提醒继续 | 1% flight,engagement 低 |
| Goal Companion | 从对话提取用户"目标"→ 定期检查进度 | 1% flight,"not sure if we want to continue" |
| Morning Digest | 用 memory+connector 推每日日报 | 还没 GA |

**核心区别**:
```
Copilot 的 proactive = 基于"你跟 Copilot 的对话历史"主动推内容
  → 你聊过旅行 → 推旅行话题
  → 你的 task 跑完了 → 通知你

你要的 proactive = 基于"你的真实生活状态"主动提醒和推进
  → 你的车险 8/15 到期 → 提前提醒 + 帮你比价
  → 你上次买洗衣液 45 天前 → 提醒该买了 + 给最低价
  → 你的保险理赔提交 2 周没回复 → 提醒 follow up
```

**区别在数据来源**:Copilot 不读你的 Gmail 来发现"你该做什么"——它只知道你在 Copilot 里聊过什么。所以它永远不知道你的车险什么时候到期(除非你主动告诉它)。

这也是为什么 Topic Continuation 和 Goal Companion 效果差——它们的"proactive"基于对话历史推断,但用户跟 Copilot 聊的不是生活全貌。

### 北美候选切入路径（非当前 Build 决策）

如果从北美市场开始，订阅管理仍是一条值得验证的候选路径；当前 Praxis 的实际 Build 决策已经调整为日本 Local。

```
Phase 1: 订阅管理(只连 Gmail)
  → "你每月订阅花 $247,其中 $47 是 3 个月没用过的"
  → 用户秒懂价值;门槛最低(Gmail vs 连银行)
  → 建立信任 + 获取邮件权限

Phase 2: 消耗品/家庭采购(已有邮件权限)
  → "你上次买洗衣液 45 天前,按频率还有 2 周"
  → "Amazon 今天打折 $6.99(比你上次便宜 $2)"

Phase 3: 账单/保险/财务(加 Plaid)
  → "你的车险 8/15 到期,这 3 家比你现在便宜 20%"
  → "你的信用卡年费下月扣,要不要换免年费的"

Phase 4: 全生活管家
  → 医疗预约 + 汽车保养 + 旅行规划 + ...
```

### 如果进入北美，为什么订阅优先于保险/医疗

- **频率**:订阅月月有 vs 保险年几次 → 低频场景养不成习惯
- **门槛**:只需 Gmail vs 需要 Plaid+医疗授权
- **容错**:取消错了能重新订 vs 约错医生/理赔搞错
- **合规**:邮件解析 vs HIPAA/保险监管
- **价值可量化**:"帮你省了 $47/月" vs "帮你管理了预约"(后者难量化)

### 跟 Rocket Money 的差异

| | Rocket Money | 你的产品 |
|---|---|---|
| 切入方式 | 连银行账户(门槛高) | 连 Gmail(门槛低) |
| 覆盖 | 只做订阅+砍价 | 全生活管理(订阅是 Phase 1) |
| 技术 | 规则引擎(匹配 recurring 交易) | LLM 理解邮件上下文(更复杂场景) |
| Proactive | 被动(用户打开 app 才看) | 主动推送(到时间了提醒你) |
| 数据存储 | 云端 | 端侧(隐私优势) |

### 用户的 5 种购物行为模式(Sandra UXR,JTBD)

| 行为模式 | 说明 | 对 personal agent 的意义 |
|---|---|---|
| **Compare products** | 对比功能/价格/品牌 | agent 持续跟踪:今天比 3 个,明天再看 2 个 |
| **Track prices** | 找最低价/等打折 | 🎯 agent 持续监控,降价主动通知 |
| **Decision support** | "which one is best for me" | private knowledge(偏好/历史)让推荐更准 |
| **Revisit past research** | 上次比到一半,回来继续 | 🎯 核心痛点:ChatGPT 无状态回来要重新问 |
| **Discover** | 基于兴趣浏览 | proactive 推荐(基于购买历史) |

### 购物漏斗断裂点

目前 AI 的购物链路:用户问 → AI 给推荐(文字)→ 用户去外部网站 → **AI 不知道买没买**。

personal agent 通过邮件解析订单确认邮件可以闭环:推荐 → 用户买了(邮件确认)→ 记住偏好 → 下次推荐更准。

### 直接下单情况

Tasks browser agent 能去 Amazon/BestBuy 操作,但结账受限(支付 autofill 还在 staging)。大多数购物用户还在"比价/推荐"阶段,不是"直接帮我买"。

## 十、Local 场景深挖——日本/韩国/东南亚

### 为什么日本 Local 是全球最高(5.7%)

不是偶然,是日本城市生活结构决定的:
1. **高密度+极丰富的线下选择**:东京一个站周围 200 家餐厅,"选哪家"决策成本极高
2. **电车换乘复杂**:同一段路可能 5 条路线/不同铁道公司/不同票价
3. **下班后社交是标准流程**:居酒屋→二次会(卡拉OK)→末班车——每步都是"附近找好的"

## 十一、两个核心技术难点

### 难点 1:怎么记住这么长的 memory,到期自动执行

**问题**:用户上次买洗衣液是 45 天前,agent 怎么"记住"这件事并在第 60 天提醒?这不是 LLM 的 context window 能解决的——context window 只有一次对话的长度,不跨天。

**Copilot 在 memory 上的教训**(你亲身经历的):
- Durable Facts(EDF)能跨会话存用户信息,但**只存静态事实**(名字/位置/偏好),不存"45 天前买了洗衣液"这种**带时间戳的事件**
- Blob 注入有效(+16.8pp context application),但全量注入会**撑爆 context**——如果用户积累了几百个购买记录,blob 太长
- Memory 写入不可靠("claims to remember but didn't write")

**解法方向**:
- 不靠 LLM memory——用**结构化数据库**(你文档里已经写的:结构化知识图谱 ~50MB/年)
- 每条记录是 `{type: "purchase", item: "洗衣液", date: "2026-07-15", estimated_next: "2026-09-01", platform: "Amazon"}`
- **定时触发引擎**(规则/cron)扫描所有记录,到期触发 → 不依赖 LLM "记住"
- LLM 只在**需要决策时**介入(比如"要不要换品牌""哪个平台最便宜")

```
端侧架构:
  结构化 DB(SQLite)        ← 存所有事件+时间戳
       ↓
  定时扫描引擎(每天/每小时)  ← 规则:"距离 estimated_next < 7天 → 触发"
       ↓
  触发后才调 LLM             ← "洗衣液快没了,当前最低价是?"
       ↓
  推送给用户                 ← "你的洗衣液大概还有一周,Amazon 今天 $6.99"
```

**关键:90% 的"记住+到期提醒"不需要 LLM,用规则引擎就行。LLM 只在"理解邮件内容"和"生成个性化建议"时用。**

### 难点 2:怎么稳定执行跨 app/网页的多步操作

**问题**:帮用户在 Amazon 下单 → 要搜索+选品+加购物车+填地址+付款——每一步都可能出错(被 bot detection 拦/页面变了/需要登录)。Copilot browser agent 在这上面踩了大量坑(你整理的文档里全是)。

**Copilot 的教训**(你的 browser agent 文档)**:
- Bot detection:改 UA/住宅代理,但 Walmart/Ticketmaster 仍打不过
- DOM 操作不可靠:pyautogui 坐标不同步 → 搬进 Edge API
- 死循环:loop detection + graceful fail
- 成本:remote browser 贵 20-34%
- 结论:browser agent 是**最不稳定的执行方式**

**解法方向——不要走 browser agent 路线**:

| 方式 | 稳定性 | 覆盖面 | 适合你吗 |
|---|---|---|---|
| **Browser agent**(模拟点击) | ❌ 最差(bot detection/DOM 变化) | 🥇 最广(任何网站) | ❌ 太不稳定 |
| **官方 API** | 🥇 最稳 | ❌ 最窄(只有开放 API 的平台) | ✅ Phase 1 优先 |
| **Deep link / URL scheme** | 🥈 稳定 | 🥈 中等 | ✅ 移动端优先 |
| **邮件/消息触发** | 🥈 稳定 | 🥈 中等 | ✅ 某些场景 |

**务实的分层策略**:

```
Layer 1(最稳): 用 API 直接操作
  → Amazon Product API(搜索+比价,不下单)
  → OpenTable/HotPepper API(预约)
  → Google Calendar API(加日程)
  → Plaid(读取交易)
  = 覆盖 60% 高频场景

Layer 2(较稳): Deep link 跳转到 app
  → 帮你组装好信息 → "点这里直接跳到 Amazon 结账页"
  → 用户在原生 app 里完成最后一步(付款/确认)
  → agent 不需要操控 UI,只做"信息整合+一键跳转"
  = 覆盖 30% 需要用户确认的场景

Layer 3(兜底): 提供步骤指引
  → 复杂/低频场景(保险理赔/政府办事)
  → agent 不代替操作,而是"告诉你下一步做什么+提醒你做了没有"
  = 覆盖剩余 10% 无法自动化的场景
```

**关键洞察:不需要 100% 自动化。** 用户的痛点不是"帮我按按钮"——是"帮我记住该做什么、什么时候做、做到哪了"。即使 agent 只做到"提醒+信息整合+一键跳转",不代替你按"确认支付"那个按钮,价值已经巨大了。

**Copilot 验证了这一点**:chat-to-task 的 89.9% completion rate 里,用户最满意的不是"agent 全自动做完",而是"agent 帮我做了 80%,最后一步我确认一下"(consent card 的存在就说明用户**接受**"最后一步自己确认")。

## 十四、当前 Build 决策与递进策略

### 第一个市场与场景

| 决策项 | 当前选择 |
|---|---|
| 市场 | **日本** |
| 场景 | **Local** |
| 第一批代表任务 | 聚会、餐厅、预约、交通和外出安排 |
| 核心能力 | 持久任务状态、约束理解、候选比较、跨平台推进、提醒和结果确认 |
| 执行策略 | API 优先，其次 Deep Link、邮件/日历和用户确认 |

日本 Local 是第一个用于验证产品的切入口，不是 Praxis 的最终边界。现有数据证明相邻需求和问题空间值得进入，但产品是否成立仍需要通过真实用户行为、任务完成率和留存验证。

### 第一阶段要验证的核心闭环

```text
用户提出外出目标
  → 补齐时间、人数、地点、预算和偏好
  → 建立可跨会话保存的任务状态
  → 搜索并比较候选地点
  → 通过 API / Deep Link / 用户确认推进
  → 写入日历、提供交通并按时间提醒
  → 根据变化继续调整
  → 确认安排已经落实
```

第一阶段的 Outcome 不是生成一份 Local 推荐列表，而是把一项真实外出事务推进到明确、可保存并可确认的完成状态。

### 通用能力仍按 action 类型建设

即使从日本 Local 开始，也不把底层架构写死为餐厅或聚会产品。优先建设可复用能力：

```text
1. 任务状态引擎：保存目标、约束、进度、等待项和完成信号
2. 搜索比较引擎：整合候选、偏好、距离、时间和价格
3. 协调跟进引擎：处理待确认、变更、提醒和跨时间推进
4. 执行路由引擎：根据能力选择 API、Deep Link、消息或用户确认
5. Public Knowledge 层：提供日本本地平台、规则、入口、限制和验证方式
```

这些能力未来可以迁移到购物、家居、汽车、旅行和其他国家市场。

### 当前递进路径

```text
Phase 1: 日本 Local 核心闭环
  → 聚会/外出任务创建
  → 餐厅和地点搜索比较
  → 持久化任务状态
  → Deep Link / 日历 / 交通 / 提醒
  → 用户确认 Outcome

Phase 2: 日本 Local 深化
  → 更多城市和 Local 类型
  → 预约确认邮件解析
  → 多人协调、变更和异常处理
  → 增加可验证的 API 执行

Phase 3: 场景或市场扩展
  → 依据真实用户数据决定扩展购物、旅行、汽车或其他市场
  → 复用任务状态、搜索比较、执行路由和 Public Knowledge 生产体系
```
