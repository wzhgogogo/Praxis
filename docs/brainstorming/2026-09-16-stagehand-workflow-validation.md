# Stagehand 跨站只读流程复验

- Status: draft / not integrated；development evidence，非 current baseline
- Date: 2026-09-16
- 污染状态：已暴露开发样本，不是 Clean Holdout；两批 Live 不构成成功率统计。
- 前序：[小探针](2026-09-16-stagehand-small-probe.md)、[现有执行器诊断](2026-09-16-browser-loop-feasibility-validation.md)

## 切片与验收

用户授权继续小型测试。固定 Stagehand 4.1.0，沿用 DeepSeek Gateway，以 TableCheck 141、Tabelog 八芳和 Sushi Sendou 为三个公开页面入口，目标为 2026-09-19、19:00、2 人。验证从选日期到公开预约选项页的只读过程，以及目标条件和页面结果能否独立确认。

预算为累计 18 次模型调用，每条路径最多 8 步、240 秒；实际两批共 17 次、186,337 tokens。另做零模型本地浏览器 Fixture 和一次零模型导航对照。依赖和 runner 均隔离于 `.eval-artifacts`，未接入产品、未改主 package 或生产执行器。探针有日期优先的阶段指令和显式动作检查，因此即使完成，也不能等同于自主端到端 Agent。

模型仅提议动作；执行前独立核对目标唯一、可见、可用，以及日期或公开链接的条件。未执行同意条款、填写个人信息、预约提交。探针检查不是生产 Policy/Authorization 集成；外部副作用数量没有独立审计，不能将静态动作限制当作副作用计数。

## 结果

| 模式 / 对象 | 观察结果 | 验收判断 |
|---|---|---|
| 真实 Chromium + 合成 Fixture | 修正探针的 XPath 前缀问题后，同页导航通过；追加异步结果及新标签页 Fixture 也通过 | 只证明指定脚本路径可执行，不是 Replay 或模型自主能力 |
| 模型 + TableCheck 141 | 两批均选中日期、提议并尝试点击条件匹配的 19:00 链接；没有观察到导航，重复动作被停止 | 未进入公开预约表单 |
| 模型 + Tabelog 八芳 | 第二批完成语言提示关闭和日期点击；两次建议点击实际 disabled 的 19:00，独立 DOM 检查拒绝 | 未完成；没有将邻近 17:00 / 20:00 冒充目标 |
| 模型 + Tabelog Sushi Sendou | 第二批点击日期后，建议点击已选中的人数 2，探针检查不支持该动作；随后无提议 | 未进入套餐页；可见时间窗口没有 19:00 不证明全天无位 |
| 零模型 TableCheck 导航对照 | Stagehand 点击同一公开链接后无导航；随后 Playwright 点击打开新标签页，Stagehand 也能枚举新页 | 公共表单读取成功，但不是模型流程通过，也未证明库存 |

第一批 7 次 / 73,816 tokens：另暴露等待不充分、动态 XPath 失效和不支持的 scrollTo。修正探针等待、标签页识别并先通过本地 Fixture 后，第二批 10 次 / 112,521 tokens，仍未完成三条流程。失败批次保留，不用第二批覆盖。

### 导航对照的证据边界

Playwright 打开的 141 页面 URL 携带目标日期、19:00 和人数 2；页面字段独立读到日期 `2026-09-19`、成人数 `2`。公开内容包含 ¥5,900 / ¥8,900 套餐、仅座位和店铺规则。目标时间在目的页的选中值未被此次字段采集覆盖，因此不能声称三个条件均已在表单生效，更不能据此声称可预约。

这是先 Stagehand 后 Playwright 的单次顺序对照，缩小了排查范围；没有随机对照，也没有查明底层点击失败根因。不能推断 Stagehand 普遍无法点击链接。新标签页被两套 API 同时发现，说明本次主要现象不是“新页已打开但 Stagehand 永远看不到”。

### 观察与验证缺口

八芳快照里 19:00 是普通 button 文本，未呈现独立 DOM 检查读到的 disabled 状态。模型重复建议该动作，说明结构化快照仍需补充可操作性信息。人数 2 的选中 class 可见；日期的点击已记录，但当前日期状态采集没有覆盖可能位于子节点的选中标记，不将点击成功视为条件生效的充分证明。

探针自身也有限制：分阶段指令、人数动作白名单、浅层控件上下文判断均会限制模型路径；不能把全部停滞归咎于 Stagehand。不同框架尚未在同一组合与评测协议下比较，不能得出 browser-use 或 Midscene 更差的结论。

## 工程判断与停止点

当前不支持直接用 Stagehand 替换整个浏览器层。更值得验证的最小组合是：Stagehand 负责候选观察/定位，现有 Playwright 负责受控执行，项目负责动作资格、执行后条件核验和证据接纳。它是下一切片候选，尚未实现或证明。

平台层验收应围绕三个跨站行为：观察暴露选中/禁用状态；执行后确认导航或条件真实变化；停滞时依据新观察决定下一合法动作。不要继续只加单个日期/人数控件特判，也不要现在堆叠三个框架。下一步若实现，应先以本轮失败建立本地行为回归，再用同样的三条流程验证，不继续无界消耗 Live 调用。
