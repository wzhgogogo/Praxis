# 2026-08-09：ToC 模糊需求与生活推荐交互摩擦

> 本文记录一个待验证的产品问题，不构成产品方案、交互方案、架构决策或 Roadmap 承诺。

## 1. 基本信息

- 日期：2026-08-09
- 项目：Project Praxis（知行）
- 主题：ToC 用户面对生活化推荐与事务时的模糊需求，以及由此产生的交互摩擦。
- 当前阶段：方向探索。

## 2. 问题陈述

### 2.1 ToB 与 ToC 的需求清晰度不同

许多 ToB 任务以明确目标开始，例如制作视频、编写代码或修改文件。用户通常已经知道要完成什么，系统主要接收和执行任务。

但 ToC 的生活场景常以模糊状态开始。用户可能只知道“今晚要吃饭”“想看点东西”或“想出去”，却尚未形成对品类、地点、预算、氛围或具体行动的明确需求。此时，要求用户先把模糊状态整理成完整指令，会把“形成需求”这一步重新交还给用户。

### 2.2 对话式澄清可能带来过高摩擦

当用户需要反复思考、打字描述、等待推荐、判断不匹配之处、再继续输入反馈时，交互链路可能长于现有内容或本地生活产品中的浏览式体验。

对普通用户而言，浏览、上下滑动和轻量反馈通常比不断通过自然语言澄清偏好更低成本。若推荐质量不足或表达偏好需要持续输入，用户可能回到既有的内容/本地生活 App，而不会把生活决策交给 Agent。

### 2.3 产品体验门槛

对于生活化推荐，问题不只在于模型能否理解一段明确的用户输入，还在于产品能否服务于尚未明确目标的用户。

需要验证的体验门槛包括：

- 推荐是否足够相关，能帮助用户从模糊状态逐步形成选择；
- 用户表达“不喜欢”“不想排队”“想换一种”等偏好时，交互是否足够低成本；
- 整个过程的时间、思考负担和输入负担，是否至少能与现有浏览式推荐体验竞争。

## 3. 仍需验证

1. 在首个日本 Local 场景中，用户带着模糊需求而非明确任务进入产品的比例和具体形态。
2. 用户为形成可执行选择，愿意进行多少轮输入、选择或反馈。
3. 推荐质量、交互成本、决策时间与用户放弃率之间的关系。
4. 用户在“浏览发现”与“明确委托完成”之间的实际切换方式。
5. Praxis 能在现有内容/本地生活浏览体验之外提供的增量价值，是否足以改变用户行为。

## 4. 讨论边界

本记录只保留问题与待验证假设。以下事项尚未形成结论，不能从本文推导为实现方向：

- 是否采用卡片、滑动、Feed、对话或其组合；
- 是否建立偏好记忆、何时读取何种用户数据；
- Explore 与 Task 是否应成为独立产品模式；
- Restaurant MVP、Stage 2C/2D 或任何 Roadmap 是否因此调整；
- 评估指标、数据集或模型调用方式如何修改。

后续只有在用户研究、原型测试或真实行为数据支持后，才另行形成产品方案或架构决策。
