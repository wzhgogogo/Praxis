- 当前阶段：从方向探索进入产品定义与原型实施

## 2. 决策

Praxis（知行）将从 **日本市场的 Local 场景**开始 Build。

这里的 Local 不是一次性的“附近有什么餐厅”问答，而是围绕一次真实外出活动形成持续、有状态的任务，例如：

```text
提出聚会或外出需求
→ 确认时间、人数、地点、预算和偏好
→ 搜索并比较候选地点
→ 协调选择和预约
→ 写入日历并通知参与者
→ 提供交通与时间提醒
→ 根据变更继续调整
→ 确认活动安排已经落实
```

聚会、餐厅和外出安排是第一批代表性任务，但不在当前阶段把产品永久限制为某一种 Local 用途。

## 3. 为什么选择日本 Local

### 3.1 市场和用户问题更具体

现有数据表明，日本用户对 Local、旅行和生活服务类信息存在较强的相邻需求。日本高密度城市环境、本地平台分散、电车交通复杂，以及聚会和线下活动丰富，使一次普通外出可能跨越餐厅搜索、预约、日历、地图、交通和消息等多个平台。

这些数据不能直接证明 Praxis 一定成立，但足以支持进入 Build，通过真实使用验证以下问题：

1. 用户是否认为跨 App 组织外出是一项持续、明显的负担；
2. 用户是否需要 Agent 保存进度并在几天内持续跟进；
3. 用户是否愿意提供日历、邮件或任务信息以换取更少的协调成本；
4. 用户是否认为“整合信息、推进下一步、最后由我确认”已经具有足够价值。

### 3.2 场景能够检验 Praxis 的核心差异

日本 Local 同时包含：

- Public Knowledge：本地平台、预约规则、交通方式、营业时间、费用和操作入口；
- Private Knowledge：用户的位置、预算、饮食偏好、同行人、日历和历史选择；
- Task State：当前处于提议、比较、待确认、已预约、待出发还是已完成；
- Agent Execution：搜索、比较、生成候选、Deep Link、写入日历、提醒和跟进；
- Verified Outcome：地点和时间已确认、预约已完成、参与者已收到信息或用户明确确认。

因此它不是一个孤立的推荐功能，而是对“理解—规划—行动—跟进—验证”完整链路的压力测试。

### 3.3 技术上可以渐进实现

第一阶段不需要先解决万能 Browser Agent。可行路径是：

1. 使用结构化数据库保存任务、参与者、时间、地点、约束和状态；
2. 使用确定性规则或调度器处理时间提醒和未完成任务；
3. 使用 LLM 理解自然语言需求、整合候选并处理变更；
4. 优先使用公开 API 获取地点、交通和可用信息；
5. 对封闭平台使用 Deep Link，把最终确认留在原生 App；
6. 通过邮件、日历事件、页面回执或用户确认更新任务状态。

这条路径能够先验证用户价值，再逐步提高自动化比例。

## 4. 第一阶段产品边界

### 要做

- 接收一项日本 Local 外出或聚会需求；
- 识别并补齐时间、人数、区域、预算和偏好等关键约束；
- 生成结构化、可持续更新的任务；
- 搜索、整理和比较候选地点；
- 保存选择过程，支持用户之后继续而不是从零开始；
- 提供地图、预约和交通入口；
- 在用户确认后写入日历，并在关键时间提醒；
- 保存任务状态，直到安排得到确认。

### 暂不要求

- 自动操作所有日本网站和 App；
- 自动支付、购票或执行其他不可逆动作；
- 一开始覆盖所有城市、平台和 Local 类别；
- 第一版同时进入购物、汽车、家居、保险和医疗；
- 用现有 Local 查询占比替代真实用户验证。

## 5. 第一阶段核心闭环

```text
用户提出真实外出目标
        ↓
Agent 建立持久化任务并补齐约束
        ↓
Public Knowledge + 实时数据生成候选和下一步
        ↓
API 执行 / Deep Link / 用户确认
        ↓
日历、邮件、回执或用户反馈更新任务状态
        ↓
Agent 持续跟进，直到结果可确认
```

第一阶段的 Outcome 不是“给出一份推荐列表”，而是至少把一项真实外出安排推进到明确、可保存和可确认的状态。

## 6. 数据和 Public Knowledge 建设方向

不先建设大而全的生活知识库，只建设日本 Local MVP 实际需要的知识：

- 城市、区域、车站和交通关系；
- 本地地点和服务类别；
- 平台能力、入口、API、Deep Link 和限制；
- 搜索、比较、预约、取消和变更流程；
- 营业时间、预约条件、费用和常见异常；
- 日语表达、本地习惯和用户决策中常见约束；
- 完成信号、来源、适用范围、版本和最后验证时间。

Public Knowledge 采用 Agent 先探索和生成候选、自动检查、人工审核及真实执行反馈共同更新的方式。目标是积累被产品实际调用和验证过的知识，而不是先追求 Markdown 数量。

## 7. 需要通过 Build 验证的核心假设

1. 日本用户确实存在需要跨平台、跨时间推进的 Local 任务，而不只是一次性搜索需求。
2. 保存任务状态、记住约束和持续跟进，比单次推荐明显更有价值。
3. API、Deep Link 和用户最终确认可以在不依赖 Browser Agent 的情况下形成足够完整的闭环。
4. 用户愿意为更少的协调成本提供必要的信息和权限。
5. Local 场景具有足够的使用频率，能够形成留存而不是一次性工具。
6. 在日本 Local 中沉淀的任务引擎、状态模型和知识生产流程可以迁移到其他生活场景和市场。

## 8. 当前结论

Copilot、竞品评测和用户研究数据为市场规模、现有产品缺口和技术路径提供了方向性佐证，但没有直接证明 Praxis 的 PMF。

选择日本 Local 作为第一个 Build 场景，是为了在一个具体、真实、足够复杂但可以渐进实现的场景中，验证 Praxis 最核心的产品命题：

> **用户是否需要一个不只给出答案，而是记住上下文、推进下一步并持续跟进到结果的 Personal AI Agent。**
