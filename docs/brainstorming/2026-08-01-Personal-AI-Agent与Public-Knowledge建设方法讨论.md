> **Not just answers. Outcomes.**

## 2. 讨论背景

Personal AI Agent 的核心价值，不只是回答问题或给出建议，而是理解用户需求和偏好，替用户规划周全，并持续推进生活中琐碎、复杂、耗时的事情。

用户痛点可以概括为：

> 很多生活事务本身并不一定困难，但步骤分散、信息繁杂，需要反复搜索、填写、上传、沟通、等待和跟进，长期消耗用户的时间与精力。

场景不应只局限于购物和旅游规划，还可覆盖：

- 购买、退换货、价格和售后协调；
- 旅行规划、预订、改签、取消及异常处理；
- 账户、订阅、运营商和家庭服务管理；
- 各类申请、证明材料准备、提交和状态跟进；
- 报销、理赔、申诉等多渠道、长周期事务；
- 搬家、维修、预约、学校和政府办事等生活项目。

保险理赔是一个很典型的复杂场景，但在整体研究中只作为“高复杂度压力测试”，不是项目必须选择的起点，也不代表产品方向应围绕保险展开。

## 3. 讨论了什么

### 3.1 产品究竟解决什么问题

Personal AI Agent 要解决的核心问题是“生活事务的端到端推进”，包括：

1. 理解用户真正想完成什么；
2. 结合用户偏好和限制制定计划；
3. 确认需要哪些信息、文件和授权；
4. 在网站、App、邮件、电话等渠道中推进；
5. 处理失败、补材料、改期等分支；
6. 持续跟进，直到获得可以验证的完成结果。

因此，它与普通问答助手的差异不是“回答得更聪明”，而是能否减少用户与不同机构、页面和流程反复拉扯的成本。

### 3.2 为什么从 Public Knowledge 开始

整个系统最基础的起点应是 Public Knowledge。这里的 Public Knowledge 不是普通百科知识，而是：

> 用户遇到一类生活事务时，通常需要做什么、需要准备什么、会遇到哪些分支、可以通过哪些渠道推进，以及如何判断事情真正完成。

Private Knowledge 则用于把通用任务落实到具体用户，例如：

- 用户主动上传的合同、票据、证件和历史文件；
- 用户授权读取的邮件和日历；
- 用户的账户、订单、偏好、家庭成员和历史操作；
- 当前 case 的进度、反馈和待补信息。

Public Knowledge 让系统知道“这件事通常怎么办”，Private Knowledge 让系统知道“这个用户的这件事具体怎么办”。

### 3.3 Public Knowledge 不应只是一批操作步骤

单纯记录“点击哪里”不够。一个可供 Agent 使用的 Task Knowledge Object 至少应包含：

```text
任务名称与用户目标
适用地区、机构、产品、渠道和版本
前置条件
用户需要提供的信息和文件
任务阶段和可执行步骤
条件分支与异常处理
不可逆或高风险动作
完成状态及验证方法
官方来源、采集时间和有效期
未确认项、冲突信息和置信度
```

公共知识的正确形态更接近“有证据、有范围、有版本、可执行、可验证的任务说明书”，而不是静态攻略集合。

### 3.4 Agent 先探路、人工优化是否可行

方向可行，而且应成为早期数据生产的主要方式，但需要把不同职责拆开：

- Agent 负责广泛发现、界面探索、轨迹录制、信息抽取和结构化初稿；
- 自动验证系统负责检查来源、结构、冲突、死路、可重放性和副作用；
- 人工负责判断真实性、处理例外、审核高风险规则和确认完成标准。

推荐的数据生产流程：

1. **Agent 探索**：搜索官方帮助文档和 FAQ，在安全环境操作网站/App，保存页面、截图、URL、时间和轨迹。
2. **结构化生成**：自动抽取前置条件、所需材料、任务步骤、条件分支和完成信号。
3. **自动验证**：检查每条关键规则是否有来源，信息是否冲突，流程能否 replay，是否存在死路或意外副作用。
4. **人工审核**：重点处理不确定内容、例外分支、资格和费用，以及付款、取消、提交等不可逆动作。
5. **上线演化**：通过真实执行结果和用户反馈发现失效知识，对受影响部分重新探索和审核。

这会把人工从“逐条从零生产”转变为“审核机器候选、处理疑难项”，从而提升速度并降低单位数据成本，但不能取消人工判真。

### 3.5 对开源项目和研究方法的梳理

#### TaskBench

- 方法：定义工具库和工具图，从工具图反向生成用户任务、步骤和参数，再经过 LLM critic、规则 critic 和人工审核。
- 可借鉴：AI 批量生成候选数据、自动过滤、人工复核的数据工厂流程。
- 问题：其 Daily Life 内容仍是抽象 API 组合，不是真实生活规则；部分 temporal graph 在代码中直接把工具两两连接，不能视为真实任务依赖知识图谱。
- 启示：可以借鉴生产流水线，不能直接使用其生活任务图作为 Public Knowledge。

#### AppAgent / AppAgentX

- 方法：Agent 在 Android App 中自主探索或观看人工演示，记录 UI 元素、截图、动作和结果；AppAgentX 进一步从历史轨迹中抽象重复操作链和高层动作。
- 可借鉴：自主探路、人工修正文档、从低层点击逐渐抽象为可复用能力。
- 问题：主要沉淀“页面和按钮怎么用”，不包含完整业务规则；UI 标识、页面和操作路径容易随版本变化。
- 改进方向：从 UI 元素说明提升为任务级知识；绑定版本和页面证据；加入分支、完成验证和风险等级。

#### Mind2Web

- 方法：由人提出真实网站任务，再通过 Playwright 演示并保存 DOM、目标元素、动作、HAR、视频和快照，最后人工审核任务和步骤。
- 可借鉴：真实任务采集格式、浏览器轨迹记录和人工 demonstration 工具。
- 问题：通常只记录一条成功路径，难以覆盖替代路径和异常分支；网站变化会导致静态数据失效。
- 改进方向：一项任务保存任务图而非单一路径，并定期 replay 检测变化。

#### τ³-bench / τ-Knowledge

- 方法：每个领域包含 policy、tools、tasks 和数据库，通过动态用户对话和工具执行完成任务，最终依据数据库状态及必须告知的信息进行评测；τ-Knowledge 进一步引入大规模非结构化知识文档。
- 可借鉴：将业务规则、对话、工具、case 状态和完成评测统一起来；允许多条正确路径，以最终状态而不是固定点击序列为准。
- 问题：规则和环境主要是人为构造的；即使在可控模拟环境中，任务和评测也出现大量歧义、错误和缺少例外的情况。
- 启示：真正困难的不只是检索，而是跨文档推理、状态变化、规则适用范围和可靠执行。

#### AppWorld

- 方法：构造模拟 App 和用户数据库；每个任务都定义初始状态、验证解法和最终状态测试，同时检查是否误改了其他数据。
- 可借鉴：用可验证的状态变化判断任务是否完成，并检测 collateral damage。
- 问题：现实网站和机构通常不会暴露完整数据库，真实完成状态可能延迟或不可观察。
- 改进方向：为现实任务设计多层完成信号，例如页面回执、邮件、订单状态、到账记录和人工确认。

#### SGD / CrossWOZ

- SGD 用 schema 描述 intent、必填字段、可选字段、结果字段和交易属性，适合建立统一任务 ontology，但缺少复杂业务规则和执行步骤。
- CrossWOZ 通过同步的用户—服务人员对话记录动态目标、无结果后调整条件和跨领域依赖，对中文用户的多目标生活事务具有参考价值，但不覆盖真实 App 操作和机构规则。
- 启示：Public Knowledge 既要有结构化 schema，也要允许用户目标在执行过程中变化。

#### OpenClaw Medical Skills

- 可借鉴：把特定任务包装成 Agent skill 的形式。
- 问题：样例 policy 数量少、来源和适用范围不完整，更接近工作流演示，不能作为权威公共知识源。
- 启示：代码仓库中的 skill 不等于经过验证的业务知识。

- 之前提到的 WikiHow GitHub 地址已经 404，不再作为可用数据源。
- 旧版 `sierra-research/tau-bench` 已明确提示任务过时，应使用当前的 `sierra-research/tau2-bench` / τ³-bench。

### 3.6 为什么这件事难做

这件事的困难需要通用地理解，不应只归因于保险等行业内部规则。

#### 1. 知识范围会组合爆炸

```text
任务 × 地区 × 服务商 × 产品 × 渠道 × 用户状态 × 时间版本
```

同一类任务在不同地区、机构、账户状态和时间可能有完全不同的要求。

#### 2. 操作知识和规则知识不同

Agent 看到页面并学会点击，不代表它知道资格、材料要求、费用、截止时间和例外规则。反过来，拥有正确说明也不代表 Agent 一定能在当前界面成功执行。

#### 3. 现实知识存在多个层次

- 通用公共流程；
- 某地区、服务商和产品公开的规则；
- 用户账户、合同、邮件和当前 case 中的私有信息；
- 机构内部规则、系统状态和人工裁量。

Public Knowledge 无法也不应该假装覆盖最后一层。系统必须把 `unknown` 作为正式状态，并知道如何询问机构、请求用户材料或升级人工。

#### 4. 完成往往是异步的

提交表单不等于完成。很多任务还需要审核、补充材料、等待退款、电话确认或线下处理。

#### 5. 正确路径不唯一

用户可能通过网站、App、电话、邮件或线下完成同一件事。系统可以保存参考路径，但应以结果和副作用为评测标准。

#### 6. 知识会持续变化

App 页面、政策、收费、资格条件和联系方式会不断变化，因此必须记录来源、范围、版本和有效期，并建立失效检测机制。

#### 7. 权限、隐私和不可逆操作

登录、上传证件、付款、取消和正式提交不能由探索 Agent 无限制执行，需要测试账户、只读模式、用户确认点和审批机制。

### 3.7 内部知识问题应该如何定位

保险理赔确实说明了一个普遍问题：不同机构、产品、地区和用户状态的要求不同，而且部分判断规则只存在于机构内部。

但这并不意味着必须先拿到所有内部知识才能做产品。系统仍然可以：

- 掌握通用任务骨架和公开要求；
- 从具体机构官网、用户合同和当前页面加载覆盖层；
- 帮用户准备、检查、提交、跟进和补充信息；
- 对不能确定的规则明确说明未知，并帮助用户向正确机构求证；
- 将新的官方反馈和实际结果沉淀为有范围、有来源的知识。

这一原则同样适用于签证、报税、学校申请、医疗、退换货、政府办事和运营商服务，不是保险特有问题。

### 3.8 数据护城河和用户飞轮

潜在护城河由三部分组成：

1. **Public Knowledge**：覆盖越来越多生活任务，并且有来源、范围、版本、分支和完成标准。
2. **执行反馈数据**：知道哪些路径实际成功、哪些步骤经常失败、哪些页面或规则发生了变化。
3. **用户 Private Knowledge**：用户使用越多，系统越了解其偏好、历史材料、常用账户和处理方式，从而减少重复沟通。

飞轮可以概括为：

```text
更多任务知识
→ 更高的任务完成率
→ 更多用户使用和真实反馈
→ 更准确的任务知识与用户理解
→ 更高的任务完成率和用户粘性
```

## 4. 形成的结论

### 已形成共识

1. 产品主线是通用的生活事务 Agent，不应围绕某一个保险场景定义。
2. 项目的基础起点应是 Public Knowledge，Private Knowledge 在具体用户和具体 case 中逐步接入。
3. Public Knowledge 不能只是网页说明或操作步骤，应是有来源、有适用范围、有版本、有分支和完成标准的可执行任务知识。
4. Agent 先探路、自动验证、人工判真的数据生产方式可行，能够降低从零采集和结构化的成本。
5. 人工审核不能完全取消，尤其是高风险、不可逆、资格判断、费用和例外规则。
6. 应保存参考路径，但以可验证的最终结果和是否产生副作用作为核心评测标准。
7. 无法获得的内部知识不应由模型猜测；`unknown`、求证和升级处理是产品能力的一部分。
8. 保险等复杂场景适合用来检验架构是否健壮，但不是当前必须选择的起点。
9. 一个人可以开始建设方法、schema、工具链和小规模种子数据，但无法单独快速覆盖所有主流生活场景；早期目标应是验证生产体系，而不是追求覆盖率。

### 仍需验证

1. 一套跨场景通用的 Task Knowledge Object schema 应如何设计，哪些字段是所有任务都必须具备的。
2. Agent 自主探索相比人工 demonstration，在不同类型网站/App 中分别能节省多少时间和成本。
3. 哪些自动检查能够真正减少人工审核，而不是只增加形式上的评分。
4. 如何可靠判断真实任务已经完成，特别是需要等待、邮件、电话或线下反馈的任务。
5. 如何检测页面、政策和流程变化，并精准触发受影响知识的重新验证。
6. Public Knowledge、用户文件和实时环境之间应采用怎样的检索、合并和冲突处理机制。

### 暂不展开

1. 具体国家或地区的 MVP 场景选择。
2. 中国大陆与其他东亚、东南亚市场的 MVP 对比。
3. 完整的商业模式、定价和获客渠道。
4. 直接自动执行付款、取消、正式申请等高风险操作。
