## 行为与验证

- 纯事实刷新待完成时，仅开放对原批次的事实调查。上下文和 Validator 都拦截搜索、查位和提前交付。H002 在普通推荐和带日期、时段、人数及未耗尽游标的推荐场景中，均实际重查原批次 `a/b/c` 三家，终态为 `PRESENT_RESULTS` 并返回 `a/b/c`。每个场景均检查了刷新请求与事实观察事件，查位调用为零。后一个场景也验证了移除待刷新标记后，搜索和查位在对照状态中可用。
- 取消与预检时的 `ActiveRead` 实例绑定。等待之后先判断同请求是否落盘，再检查新用户事件、目标范围和读取所有权。HTTP 回归把旧操作停在最后一道取消前校验之后。新批次从 `a/b/c` 切到 `d/e/f` 后，旧刷新和旧批次操作均返回 409。另验证了新读取接手时，旧定位和旧刷新返回 409，新读取继续运行且旧操作没有落盘。同店 G1 正常完成推进版本后，新追问仍可提交，正常取消旧 G1 后也可以继续。
- 同一请求用原 `requestId` 和原 `taskVersion` 重送得到 200。H002 两个并发消息与已完成重试共用一次用户事件、一次读取。两个相同的 HTTP 刷新同时到达 Runtime 派发点时，一次写入，另一次由 `duplicateEvent` 返回，消息、刷新事件和读取都各发生一次。
- 普通 `serves beer` 及裸写 `beer`、`ビール`、`啤酒` 仍可由明确的餐饮类别支持。无酒精或无麸质啤酒不会由普通 `brewpub`、`beer bar` 兜底。裸类别、GOOGLE_TYPE、CATEGORY 均覆盖新模型判断和已有 MODEL_JUDGMENT 的接纳。明确商家原文两种限定词均通过。
- 当推荐文案为空时，条件区与预约按钮间的实际距离为 12px。六份截图逐张查看，条件文案及状态对齐，按钮和条件行在截图中清楚分离。
