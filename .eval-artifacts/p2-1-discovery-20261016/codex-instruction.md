## 为什么做这一批

第一阶段和 P2-0 中 4 次 CAPABILITY_MISS 的第一卡点都在找店。复核者从 22 份校准输入的 `nativeDiscoveryFunnel` 中逐次核对，原因是同一类：

| 用例 | 来源上实际发生的事 |
| --- | --- |
| h001（omakase，涩谷） | Planner 把 HARD 原文 `omakase` 直接作为 Tabelog 的 `sw`。地区 A1303 内只有 3 家，2 家在半径外。之后的类别扩展：KF-H001 那次模型选了 sushi 并去掉关键词，得到 197 家，于是交付；p1fB-h001、p1g2-h001-a4、p20-h001 三次中，模型先试 `sushi/?sw=omakase`（0 家），再试 `washoku/?sw=omakase`，再试 `washoku/`，没有得到可读的类别列表：p1fB 撞上来源 6 页上限（`NATIVE_LISTING_PAGE_LIMIT`），p20 执行失败（`AGENT_EXECUTION_FAILED`）；p1g-h001 的类别扩展为 `NO_SAFE_ACTION`。P2-0 那次的见证店 Sen、Matsumoto 都没有进入候选 |
| 神乐坂（kaiseki） | 语义输出为 `kaiseki restaurant`（Gold 是 `kaiseki`）。`sw=kaiseki restaurant` 在全东京和 C13104 都是 0 家，Tabelog 以 `EXTRACTION_FAILED` 结束，没有尝试改写或类别 |
| KF-H005（local food） | `sw=local food` 在全东京只有 2 家，C13102 内 0 家，Tabelog 结束 |
| 吉祥寺（tempura） | `sw=tempura restaurant` 0 家；模型自行在全国列表、`tempura/?sw=restaurant`、A1330、A1320 之间转换，见证店未出现 |

共同点：

1. **检索词是用户原话的机械投影**（`discovery-planner.ts` 的 `positiveHardKeyword`：第一个正向 HARD 条件的原文）。"kaiseki restaurant""local food"在来源上不是有效检索词。
2. **类别扩展是后补的**：只有在关键词首批全部查完、同一来源续读时才发生，一次机会，而且与选地区共用每个来源 6 页的上限。
3. **0 家不触发改写**，直接结束该来源。
4. **找店时不使用日期、时间、人数筛选。** 两个来源的公开搜索都支持（原 C7）；现在先找店，再逐家打开日历。

本批同时解决这两件事：检索词和类别由 Agent 规划（P2-1a），以及查位请求在找店时就用来源的空位筛选（P2-1b）。两项分开实施、分开测量。

## 原则（违反任一条即不通过）

- **Agent 负责判断，代码负责核对。**
  - 检索词、类别和是否改写由 Agent 根据请求和页面上观察到的内容决定。
  - 代码只核对：类别链接是当前页面上观察到的、在同一地区范围内；检索词符合第 4 项的格式约束；日期、时间、人数、地点只用权威值。
- **不写死。** 共享层不出现站点名、地名、菜系、"omakase→sushi"之类的映射表或用例 ID。来源 Pack 只放来源自己的 URL 语法和页面解析。
- **检索只影响"找到谁"，不影响"谁合格"。** 每个候选的 HARD、身份、半径、空位仍按现有规则逐家核实。来源搜索结果里的时段只是线索，最终空位仍以门店自己的日历或查位入口为准。
- **检索词实验的教训**（76213a4）：
  - 不要求模型给出逐字引用来证明"0 家"，模型给不出；
  - 空结果由解析器和页面的明确空状态判定；
  - 类别入口是可行路线。
- 一次只改一个变量；先红后绿；涉及执行器、Guard、Source Pack、浏览器 Adapter、读取组装的改动，`test:browser:fixture` 必须全绿。

## 4 P2-1a：检索规划由 Agent 负责

ADR 批准后实施。要求：

1. **检索输入**：Planner 不再生成 `keyword = HARD 原文`。发现请求携带全部正向条件（文本、强度），以及检索规划结果。
2. **检索规划**：
   - 在需要检索表达式、且还没有页面可观察的来源（TableCheck 的 `search_text`、Google 文本搜索），由 Agent 先给出一个短检索词，或明确"不用检索词"。
   - 每次请求最多多用 1 次模型调用。可以并入现有决策调用，不必单独调用。
   - 在目录型来源上，选定地区后由 Agent 根据当前页面上的类别入口和列表，选择类别、检索词、二者组合，或不检索。
3. **检索词的格式约束**（共享层的通用核对，不按站点）：
   - 最多 3 个词；
   - 不含数字，不含请求中的地点名、日期或时间文字；
   - 必须注明对应哪一条正向条件（`criterionRef`）；
   - 负向条件、价格、人数、时间不得进入检索词；
   - 不合格时拒绝，记录原因，回退为不加检索的通用列表或类别。
4. **类别的核对**：
   - 链接在当前快照中可见；
   - 与已选地区同一列表根（沿用 ADR-0040 的地区核对）；
   - 去掉旧检索词时，使用页面自己的筛选移除链接，或 Pack 的语法。
5. **稀疏和空结果**：
   - 选定地区后，结果少于一批（5 家）或为明确空状态时，允许 Agent 在**读详情之前**改写检索，每个来源最多 2 次；
   - 已经观察到的匹配结果保留在队列前面，不因改写丢失；
   - 每次改写计入页数和模型调用；
   - 把选地区和检索的页数分开计数，或者在不提高全局上限的前提下调整来源页数上限，在 ADR 中说明。
6. **空状态识别**：神乐坂 0 家时以 `EXTRACTION_FAILED` 结束。先确认是不是 Tabelog 英文页的空状态没有被 `isExplicitEmpty` 识别，再用真实快照做 Fixture 修正。
7. **删除**：被替代的"首批查完后才允许一次类别扩展"逻辑删除，相应调用者和测试一起删除或迁移，不留两套路径。
8. **测试**（先红后绿）：
   - 稀疏关键词 → 类别；
   - 0 家 → 改写；
   - 改写次数用完 → 如实结束；
   - 越出地区的类别链接 → 拒绝；
   - 含日期、人数、地点或数字的检索词 → 拒绝；
   - 推荐目标不受影响；
   - 预算上限；
   - 真实 Chromium 上的动态 Fixture 覆盖类别入口和空状态。

做完后进行**探测检查点 A**：与第 2 项相同的 10 次探测。

## 5 P2-1b：搜索级空位筛选（原 C7）

在 P2-1a 的探测检查点 A 之后实施。要求：

1. **只用于查位目标**（语义目标为 AVAILABILITY，且有日期和人数）。推荐目标不使用。
2. **值的来源**：日期、时间、人数只用请求中的权威值，由执行器填写，Agent 不能改值。
3. **实现方式**：二选一，在 ADR 中说明理由：
   - Agent 操作页面上观察到的筛选控件；
   - 来源 Pack 用自己的 URL 语法加上筛选参数。

   观察时记录到的公开参数：Tabelog 为 `vac_net`、`svd`、`svt`、`svps`；TableCheck 为 `date`、`time`、`num_people`、`availability_mode`。
4. **应用核对**：必须在页面上核对筛选确实生效（页面状态显示所选日期和人数），否则视为未应用，回退为不加筛选的列表，并记录。
5. **筛选为空**：只说明这一页没有线索，不能据此判"无位"或"来源穷尽"。回退为不加筛选的列表，记录回退原因。
6. **线索的用法**：结果卡片上的时段只作为排序线索。不得把它当作空位证据，交付前仍按现有规则到门店日历查位。
7. **网络边界**：
   - 目前 Tabelog 目录文档的已审核语法只允许 `sw`。新增参数要同步更新三处：Pack 的已审核读取规则、Recorder 的安全参数表（`vac_net` 目前不在其中）、外层 `reviewed-reads.json`。
   - Guard 准入不放宽到这些参数之外。
8. **测试**：
   - 筛选生效时，列表只含筛选结果；
   - 筛选未生效时回退；
   - 筛选为空时回退；
   - 推荐目标不加筛选；
   - 权威值不可被模型改写；
   - Recorder 能忠实录制；
   - Guard 拒绝未审核参数。

做完后进行**探测检查点 B**：同样的 10 次探测。

## 6 检查点的比较方式

| 检查点 | 代码 | 用途 |
| --- | --- | --- |
| 基线 | 当前代码 | 起点 |

- 每个检查点写明唯一的变化，并固定 Gold、日期规则、预算和模型配置。

- CONTROL 退步时（例如中目黑的见证店不再进入列表，或半径内家数明显减少），先查原因再继续。
