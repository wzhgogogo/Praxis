# 评测器与测试体系复核

- 复核时间：2026-10-15 17:30 北京
- 复核者：独立复核（Claude），非实现者
- 依据：
  - 分支 `codex/feat-live-restaurant-read-path`，HEAD `de2be7e`；
  - 已合入的 Eval Skill 2.0 和 Test Skill 1.3；
  - 此前的复核：`EVAL-DESIGN-LOCALIZATION-REVIEW-20261012`、`TEST-METHOD-OFFLINE-LIVE-GAP-REVIEW-20261012`、第一阶段签收。
- 方法：只读代码，不运行测试，不调用模型，不访问网络。行号以 `de2be7e` 为准。
- 不含：逐条测试的退役清单（只给出标准和已确认的几项）、`src/eval/restaurant/semantic` 下的语义评测。

## 结论

1. **评测器不需要推倒重写。** 它最有价值的部分保守、经过多轮修补：展示结论的证据链核对、TableCheck 原始 trace 核对、无结果范围核对。这些应作为新结构里的"环节判定"保留下来。要做的是在外面补上 Eval Skill 2.0 要求的东西：
   - 见证 Gold；
   - 七类结果与严重程度；
   - 时间和资源指标；
   - 跨运行汇总。

   同时修掉三处"自己证明自己"的问题。
2. **测试体系最大的问题不是测试太少，而是"测的和跑的不是同一套组装"。** Live Runner、Web 服务和组合测试各自手工组装一遍，参数已经漂移：
   - 找店额度上限只有 12，正是这种漂移造成的；
   - 默认门禁也不包含任何真实浏览器测试。
3. **有两样东西已经可以直接用，成本很低：**
   - 一是第一阶段约 20 次运行的人工签收归类，可以拿来校准评测器；
   - 二是为每次组装提取一个公共函数。

## 一、评测器（`diagnostic-evaluator.ts`，1,051 行）

### 现状

单个文件，一个入口 `evaluateRestaurantHybridLiveArtifact`。它直接读 `result.json` 的原始 JSON，输出 6 个维度：

- AUTHORITATIVE_CONDITIONS
- REQUIRED_EVIDENCE
- INVESTIGATION_BEHAVIOR
- FINAL_CLAIM
- COMPLETION_OUTCOME
- RESOURCES

对应的测试（`diagnostic-evaluator.test.ts`，39 个用例）全部使用手工构造的 artifact，没有一份真实运行产物。

### 保留、改造、新增

| 部分 | 处理 | 理由 |
| --- | --- | --- |
| `assessPresentedCandidate`（第 660–823 行）：身份、区域、HARD、新鲜度、offer 一致性 | **保留**，作为"展示结论支持性"判定 | 规则细、保守，多轮复核中没有误判为通过 |
| `rawTableCheckCurrentResult`（第 575 行起） | **保留** | 唯一一处真正拿来源原始观察核对的逻辑 |
| `assessNoResult`（第 831–949 行） | **保留，改一处** | 范围核对有用；但只认 Agent 自己发出的 `END_READ`（第 918–919 行），系统主动结束一律判为未评价。P2-0 第 4 项会增加结构化结束原因，这里随之改为也认系统结束 |
| 条件比对 `compareCriteria`（第 241–287 行） | **保留规则，补等价表** | 只按字面比对。第一阶段每次 "tempura" 对 "tempura restaurant"、"team dinner" 对 "suitable for a team dinner" 都判为 UNKNOWN，全靠人工逐条核对 |
| Tabelog 空位日期和人数核对（第 776 行） | **改** | 拿生产代码从请求复制过来的字段，再去和请求比，必然一致（P0-1）。应改为与交付后 GET 原始响应或录制的 `find_vacancy` 响应核对 |
| 营业时间核对（第 761 行） | **改** | 直接调用生产代码的 `openingHoursForRequest`。生产代码和评测器用同一个函数，这个函数出错两边都看不出来。按 Eval Skill §3，应由评测器独立实现，或用固定样例表 |
| INVESTIGATION_BEHAVIOR | **扩展** | 只检查"同一候选重复查位或读信息"。P1-G2 h001 的 24 步死循环在这一项仍是 SATISFIED，因为被拒的动作和执行失败的动作不算"访问"。应增加：被拒动作数、连续无进展步数、重复失败的同类动作、同一 URL 重复加载 |
| RESOURCES | **改** | 只和运行记录里声明的上限比较。找店阶段声明 120、实际生效 12 时，它看不出来。P2-0 第 2 项会记录实际生效的限额，这里改为与实际生效值比较，并报告两者不一致 |
| 结果分类 | **新增** | Eval Skill 2.0 的七类结果和 S0–S4 严重程度，目前没有实现。第一阶段这一步全靠人工完成 |
| 见证 Gold 接入 | **新增** | 有见证文件时自动生成"见证漏斗"：是否发现、查位结论、是否展示，并给出候选卡点。无结果时就能区分"见证店有位却没交付"（能力缺口）和"如实没结果" |
| 时间分解、重复加载 | **新增** | 10/12 评测设计复核已给出算法和一次性脚本，应改成 Runner 或补评工具的固定输出 |
| 跨运行汇总 | **新增** | 按"环节 × 严重程度"汇总，用来决定"先修什么" |

### 建议的新结构（同一入口，分层实现）

1. **读取层：** 把 `result.json` 解析成有类型的运行记录，之后不再到处用 `asRecord` 取字段。生产 State 改版时，只改这一层。
2. **外部 Gold 输入：** 冻结用例、见证文件、交付后 GET 原始响应、条件等价表。都按 Eval Skill §5 冻结，并记录 SHA。
3. **环节判定：** 理解请求、地点、发现、身份与事实、查位、Agent 行为、结束。现有三段核对逻辑放进这一层。
4. **结果分类与严重程度：** 由环节判定和外部 Gold 推出，不读生产代码给出的合格判断。
5. **指标：** 时间分解、重复加载、资源与实际生效限额。
6. **报告和跨运行汇总。**

### 用第一阶段的人工归类做校准

第一阶段 P1-F、P1-G、P1-G2 共有约 20 次运行，复核者给出过逐次的人工归类，记录在签收复核和各批复核中。把它们整理成一份"人工标签表"，作为评测器的校准集。

- 新评测器上线前，结果分类与人工标签逐次比对，报告一致率和每一处分歧。
- 分歧只能通过改评测器或改人工标签（写明理由）来消除，不能为了一致而放宽规则。
- 这些运行已经暴露，只用于校准评测器本身，不用于判断产品能力。
- 产物中的整页快照不进仓库，校准只需要 result.json、见证和交付后 GET 原始响应。

### 条件等价表（需要用户决定方式）

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A 审核过的等价表（建议）** | 一个版本化文件，逐对记录"Gold 写法 ↔ 系统写法 ↔ 是否等价 ↔ 审核人"。评测器只查表，查不到仍为 UNKNOWN 并输出待审项 | 确定性、可审计；人工判断一次，以后复用 | 新写法要人工补表 |
| B 固定版本的模型评判 + 人工抽检 | 用固定模型和固定 Prompt 判断等价 | 覆盖新写法 | 引入模型调用和不确定性，需要另做校准 |

第一阶段出现过的差异不超过 10 对，A 方式一次就能补齐。

## 二、测试体系

### 1. 三套各自组装的链路，参数已经漂移（最重要）

| 组装位置 | 找店的浏览器模型上限 | 每来源找店操作上限 | 循环步数 / 拒绝上限 | 浏览器额度是否整单共享 |
| --- | --- | --- | --- | --- |
| Live Runner（`run-hybrid-live-read.ts` 第 404–455 行） | 未传，实际为 12 | 传了 80 | 30 / 5 | 是 |
| Web 服务（`local-web-server.ts` 第 385–440 行） | 未传，实际为 12 | **未传，实际为 24** | 30（Live 模式） | 是 |
| 组合测试 `native-discovery-composition.test.ts`（第 214–224 行） | 未传 | 未传 | **20 / 默认 3** | **否**：`browserBudget` 传的是 `undefined` |
| 组合测试 `hybrid-read-composition.test.ts` | 各用例自配 | 各用例自配 | **6–12 / 默认 3** | 各用例自配 |

- 组合测试从不共享额度计数，所以"累计 12 次后找店失败"在离线永远出现不了。这正是找店额度问题一直没被发现的原因。
- P1-G 修复 B 的报告说组合测试"使用与 Live 相同的 `createHybridReadComposition`"。这只在调用同一个函数这个意义上成立，传入的参数并不相同。

**建议：** 把"生产组装"提成一个函数，例如 `createLiveReadAssembly(config)`，Runner、Web 服务和组合测试都调用它。

- 测试只替换外部传输：模型、Google、页面来源和时钟。
- 限额只从同一份配置读取，测试要改限额必须显式覆盖，并在用例名中写明。
- 删掉三处手工组装。

P2-0 第 2 项已经要求"Runner 与 Web 拿到相同的生效限额"，这一项把它做彻底。

### 2. 默认门禁不含任何真实浏览器测试

- `npm test` 的文件范围不包括 `src/harness/browser/`。真实 Chromium 的测试（`browser-read-fixture.test.ts`，59 个用例）只在 `test:browser:fixture` 中运行。
- "四门禁全绿"因此从未覆盖真实浏览器行为。Guard 只拦第一跳的问题就是这样漏掉的：Guard 单测用的是假 route（`playwright-read-network-guard.test.ts` 第 154–170 行），按 Test Skill 1.3 属于"用假对象预设运行时行为"。

**建议：** 改动涉及浏览器、Guard 或执行器时，`test:browser:fixture` 列为必跑门禁，报告中单独写明。这本来就是 Test Skill 矩阵中"Provider/Browser Adapter"一行的要求，只是执行中被"四门禁"替代了。P2-0 第 1 项的 Guard 真实浏览器测试应放在这个套件里。

### 3. 组合测试里的模型是剧本

- 组合测试里的模型都是按脚本返回动作。它们能证明"这条路径走得通"，证明不了"模型在这种状态下会怎么做"。
- P1-G2 h001 的"搜索失败 ↔ 结束被拒"死循环，只有真实模型或决策回放能复现。

**建议：**

- 把每次 Live 中的关键决策点（死循环起点、被拒后的下一步）加入回放种子，用 `run-decision-replay.ts` 做真实模型回放。这就是 Eval Skill 的 L3 层。
- 回放进入每批的必跑检查，次数按预算限定。

### 4. 录制不能回放

10/12 测试方法复核已指出：只要有一页不合格，整次录制就作废。P1-F 和 P1-G 的全部录制都是 NOT_REPLAYABLE。在这一点修好之前，Live 中出现的问题无法变成离线回归测试。

**建议：** 按页判定，排在组装统一之后。

### 5. Web 入口的并发问题（结构上可以确认）

- `persistent-restaurant-agent.ts` 第 1023–1045 行的 `finishInterruptedLiveRead`，会在每次 `project()` 时把"没有登记在 `activeReads` 中、且处于 UNDERSTANDING / SEARCHING / SELECTION_REQUIRED 阶段"的任务判为 `EXECUTION_FAILURE`。
- 新建任务时，`createConversation` 之后先执行 `applyMessage`（第 395 行），其中包括一次语义解析的模型调用；读取在第 833 行才登记到 `activeReads`。
- 在这几秒的窗口里，任何一个列表或查询请求都会把新任务判为中断。

这是 10/9 复现过的问题，代码结构未变。Live 评测走 Runner、不经过 Web，所以评测永远看不到它。**必须在任何真实用户试用之前修好**，并在统一组装后的 Web 组合测试里覆盖。

### 6. 无界等待

`local-web-server.test.ts` 的 W12 等用例中，`await restaurant.started` 没有超时（第 956、995、1164、1228 行）。前置条件不满足时，测试会一直挂着，而不是失败。按 Test Skill 1.3，这类等待都要改成有界。

### 7. 测试退役

本次没有逐条清点。退役按 AGENTS.md 和 Test Skill 1.3 的标准判断：只验证已被替换实现的测试、与真实运行时行为不符的假对象测试，以及在统一组装后变得重复的手工组装测试。已确认要替换的有两类：

- Guard 的假 route 重定向用例；
- 组合测试中的手工组装部分（随第 1 项替换）。

## 三、建议顺序

当前 P2-0 进行中，下面两项排在它之后：

1. **T1 统一组装与门禁**（先做，因为它决定之后所有离线测试是否可信）：
   - 提取生产组装函数，Runner、Web、组合测试共用，删除手工组装；
   - 涉及浏览器的改动必跑 `test:browser:fixture`；
   - 修 Web 并发问题和无界等待；
   - **验收：** 用统一组装重写一个"累计浏览器调用超过 12 次后再找店"的组合测试。在 P2-0 修复之前的提交上它必须失败，之后通过。另加一个 Web 并发的组合测试，先红后绿。
2. **E1 评测器第一切片：**
   - 读取层、见证 Gold 接入、七类结果与严重程度；
   - 条件等价表；
   - Tabelog 交付改用交付后 GET 核对，营业时间改为独立实现；
   - INVESTIGATION_BEHAVIOR 补充无进展检测；
   - **验收：** 对第一阶段约 20 次运行离线补评，结果分类与人工标签逐次比对，报告一致率和全部分歧。不调用模型，不访问网络。
3. **之后：** 录制按页判定（L2）、回放进入常规检查（L3）、时间分解自动输出。这些可以与第二阶段的找店改进并行。
