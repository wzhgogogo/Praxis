## P1-D：两处必须在 P1-F 前补

### 1. 地点解析：Ebisu 被解析到美国佛罗里达的一家餐厅

`resolveNamedNearbyLocation` 用 Google Text Search 查 "Ebisu"，不带任何地理偏好，然后只按"显示名完全相同"过滤。

- 结果只有一家显示名为 "Ebisu" 的日本料理店（Jupiter, FL，类型 `japanese_restaurant`），于是被当作权威地点。
- Agent 其实选对了 Tabelog 的 "Shibuya & Ebisu & Daikanyama"，前五家都在恵比寿一带，但它们与佛罗里达坐标的距离约 2,184 万米，全部判为越界。
- 报告如实记为失败，没有替换成东京坐标。

这是通用缺陷，任何与外地店名、地名同名的地点都会中招，而且 P1-F 的新地点变体正好有 "near Ebisu"。改法应当通用：

- 解析时用本次运行已知的位置上下文（用户位置或评测位置）做 `locationBias`；
- 查询是地区类说法时，优先地理类型（sublocality、neighborhood、locality、交通站点）；
- 结果距位置上下文过远时，按"地点有歧义"处理，不能静默接受。

不允许加城市名、国家码或地名常量。

### 2. "附近"类请求的地区选择没有经过真实探测

删除地区表之后，所有只有坐标、没有地名的请求（已知可行 5 例与原版实时 5 例都是 "nearby"）都要靠 Agent 自选入口。

- 现在给浏览器模型的 `goal.location` 在这种情况下只有经纬度和半径。`addressComponents` 只在有地名时才提供，而 Playbook §8 第 3 条要求两种情况都提供。
- 被删除的东银座坐标锚点原本服务的就是 kf-h002 与 kf-h005 的评测点；kf-h002 在 P1-E 正是经这条路径交付的。
- 本批 6 次探测都是有地名的请求，"附近"类只有一个离线测试（模型是剧本）。

需要：

- 为只有坐标的位置补充一次地址组成部分观察，作为来源事实交给 Agent，不能变成地区代码；
- 用剩余的 2 次 P1-D 探测预算，在 Ginza 与 Shibuya 两个已知可行评测点上真实验证。

## 检索词实验（隔离分支，未合入）

规格三项都已实现：

- **(a)** Agent 的 `retrievalHint` 只能由已观察店名中的词组成。
- **(b)** 0–1 个结果时，可以换一次词（`REFINE_RETRIEVAL`），或改走类别入口，只允许一次。
- **(c)** `REPORT_NO_RESULTS` 须满足：引用的原文出现在当前可见文字中、解析结果为 0、结果区不忙、仍绑定当前查询。

离线 8 组正反例通过。需要补的有：

1. **引用校验偏弱。** 现在只要求 `snapshot.text.includes(reason)`，不检查长度和内容；一个字母或一个页面上本来就有的词也能通过。它真正要防的是"解析器漏解析、页面其实有结果"的情况，而且一旦通过，来源会被记为已穷尽。至少要求引用有一定长度、不能只是当前查询词，并在结果区或计数区附近出现。
2. **效果未证实。** 0 次模型回放。原始 decisions 保存了完整 messages，可以对 kf-h001 #24–28、kf-h005 P1-E #3–8 和本次复测 #3–7 做注入式回放：只补入新的 pageActions 与 `retrievalHint` 字段。
3. **线格式放宽。** `requestedState` 的 JSON Schema 从枚举放宽为任意字符串（用来携带搜索词），解码端仍按动作逐一校验，可以接受。

合入与否由用户在看过回放后决定（ADR-0041 当前为 Proposed）。
