## 1. Google 日文名的已有能力与缺口

现有生产 [GooglePlacesClient.placeDetails](../../../src/integrations/google/google-places-client.ts) 按同一 Place ID 读取 `/v1/places/{id}`，不重新按名称找店，**但方法没有语言参数，也没有发送 `languageCode`**。`GooglePlacesRawPlace.displayName` 当前只声明 `text`，未保留语言码的类型；生产 `placeDetails` 字段掩码还包含地址、电话等，并非专门的名称请求。因此不能把“已能按 ID 读取”写成“已接好日文名”。

平台能力有本项目的真实原件支持，无需本轮联网推测：批次2 [prepare-retrieval.mjs](../c-batch2/prepare-retrieval.mjs) 在评测传输层为相同 ID 加 `?languageCode=ja`，读取并验证响应 `id` 与原 ID 相等，已经保存11份成功日文响应。该评测包装尚未成为生产接口。本轮只复核原件，没有再次请求 Google。

拟接线时：按原 Place ID、显式日文、最小名称字段 `id,displayName` 读取；先验证响应 ID、非空原文和实际语言，不要求平台一定返回日文字形。该名称只作为 **来源给出的独立检索词**，不覆盖原 Google 候选，不替代电话/地址/分店核对，不由模型翻译。和已试词相同则不重复搜索。现有片段规则保持原样：模型只提出 Google 原名称的真子串，代码逐字定位，一店至多一次片段模型调用，拒绝后不修复调用；不把日文来源名冒充原英文名称的片段。

每个需要额外日文名的 Place ID **增加1次 Google Place Details**，模型增加0次；两个来源应共享同一次运行内的名称结果，而不是各请求一次。已读到合格日文名称时无需再请求。本次四家已有三家的该 ID 日文原文，若下一批复用冻结数据，只有 Beef Kitchen 需要新增1次；若全部重新取四家则最多4次。Google 请求独立计 Google 账，不计评测网站 GET。单价/账单金额本轮未查询，不能从请求数推定价格；应使用最小字段掩码并在获准实测后报告实际用量。

**检索次序与当前合同的差异：** 用户方向是原名 → 合法片段 → Google 日文名。现有生产最多两次检索，所以这会增加第三次检索。更关键的是：当前 Tabelog 在一轮读满五个详情后直接退出，甚至不再提议片段。只在末尾加日文词不能解决已耗尽的详情名额。任何第三次检索和名额分配都只是本报告的提案，未实施，也未提高现行上限。

原首次37家保持原分母：旧29家13正确/9未接纳/7环境失败；新8家6正确/1未接纳/1环境失败；错认0。合计19正确、10未接纳、8环境失败。环境中断影响 **8/37（21.62%）**；完成的29家中正确19家（65.52%），不能把八家未知补成成功或未接纳。

### 现有超时/重试是否合理

- 已完成159次的 GET 中位2.863秒、P95（nearest-rank）5.861秒、最大14.745秒；另有一次12.379秒成功。现有20秒能覆盖这些成功长尾，**没有证据支持缩到10秒，也没有超过20秒后会成功的数据支持加长**。保留20秒是当前有证据的有界选择，不是最优时限已证明。
- 原评测按用户合同：至少间隔30秒、20秒期限、失败不重试、不带Cookie、不跟跳转；连续三次失败按“连续请求”统计，任一成功会清零。失败间有成功请求，因此不能把四个不同用例的超时误认成违规越过三连停批。
- 生产 `BrowserTaskExecutor.navigate` 默认至多20秒且受剩余候选/全局期限限制；导航运行时失败后关闭会话，没有通用连接失败重试。Tabelog 另有一个明确忙碌页的1秒等待、每候选一次重读；它是收到可观察忙碌页后的特定规则，不是本批八次连接错误的重试。Google客户端独立8秒期限，和本批错误无关。上述均只读代码，未改B文件。
- 暂不加通用自动重试。下一次获准来源实验应在同一次请求中记录开始、收到响应头、正文完成、Abort原因及脱敏的底层错误代码，区分连接失败/正文超时/HTTP429/来源结构变化；不记录密钥、Cookie或完整请求头。若之后要增加一次重试，应独立有预算、只读幂等、总期限不延长、失败/成功分开保存，限流按原合同停下；本次不批准或实施这些变更。

## 4. 两个待用户决定的方案

两个方案是从当前244/257出发的**替代选项，不是叠加授权**。先做已保存数据的离线验证，任何身份规则不变：同名不能认同店，门牌/楼层/分店/邮编冲突仍拒绝，错认目标0。候选详情总上限仍5，不能重置或把认证详情预置为生产输入；S0立即停，不为结果改Gold、Prompt或评分。

### 方案一（建议先做）：复用三份日文原名与首屏，完成有界身份诊断

先在新的获批实现切片中增加服务器端同ID日文名入口，运行时共享一次结果；检索词按原名、一个合法片段、日文全名去重。**需用户批准第三次检索，并明确详情分配**：建议前两个词至多使用4个详情名额，为日文词保留第5个；日文名缺失、重复或没有新候选时，把保留名额还给已观察候选。每个已取得的候选仍按既有接近程度排序，累计5不重置。这个4+1策略也可能把原先第5个正确候选挤掉，属于需要验证的新调查策略，不能凭本报告直接采用。

先用原冻结37家、前四复跑及后续补页语料做成对离线验证，特别保留既有23个接纳及 nr-010/022/026；只改变上述名称入口和名额分配。未知/缺页不作PASS。不能维持现有接纳和零错认就停在离线，不消耗来源额度。T 单字不满足现行最短2字符片段，不能为了给T制造片段而放宽规则；可在无合法片段时跳过该词，再走来源日文名。

然后复用 Sancho/T/Sumi 已保存的同ID日文响应与搜索原文，Beef 只取一次日文名及由它给出的首屏；冻结可观察的候选清单后仅补执行路径需要的详情（不按Gold直达）。精确缺页清单须在任何GET之前物化、冻结、交复核，不把旧认证页偷偷当本次抓取。用本批已保存的合法片段模型响应作显式Replay/fixture，模型遵循率留给后批，不能声称验证了 Prompt@3 的真实语义。

预算：**Google≤1、公开GET≤13（Beef日文首屏1 + 缺少的详情≤12）、模型0、Live0**，不需提高257总额。按 nr-007/008/019/025 固定顺序、每店详情总5、GET间隔≥30秒/20秒期限/失败不重试，任何额度不足立即记 UNKNOWN。本方案可能无法补全四家，不能预先承诺4/4；只报告限定的冻结来源身份前缀结果，以及第三词首次贡献的实际接纳数，不称作37家新的真实通过率。它不会重新测量剩余四个网络用例。

预期依据：三份日文首屏均已有认证店，Beef的更短英文片段已有命中线索；最终身份增量仍未测。先得到最小缺页清单和名额分配回归，再决定是否需要扩大实测。

### 方案二：完整的新鲜身份前缀批次，同时确认剩余四家网络影响

若用户希望直接取得当前来源的完整数字，在同样先过离线不退化、身份不变、第三次检索及详情策略获批后，运行以下两个分组，Google Tabelog直链继续隐藏：

- 检索组4家：原始Google字段 → 原名 → 合法片段 → 同ID日文来源名称 → 实际观察详情 → 原身份核对。每家最多3个检索、5个详情，最多8 GET，共 **32 GET**。四家日文名各新读一次，Google≤4；片段模型每家≤1，共≤4。
- 环境组4家：nr-009、013、015、G4-ND-002，只用当时的两词生产合同重新跑完整身份前缀，每家最多2检索+5详情，最多7 GET，共 **28 GET**；模型每家≤1，共≤4。已获独立复跑4/4的前四家不再重复花额度；该组不同时加入日文第三词，以便保留其连接/两词路径诊断范围，不能把它与检索组算同一策略通过率。

合计上限 **公开GET60、Google4、模型8、完整Live0**。从当前244算需共享GET上限至少 **304（比257增加47）**；本报告没有分配或消耗该额度。如果先执行方案一，再选择方案二，必须按届时真实账本另算，不能复用这个“增加47”的余额计算。

20秒、间隔≥30秒、不带Cookie、不跟随跳转、失败不重试、连续三次网络失败停批，逐次先记账；模型/Google凭据仅在后续明确获准后由Node `--env-file` 注入，不从聊天或文件读取。保存HTTP阶段信息和错误代码不增加额外探测请求。评测仍仅身份前缀，不运行完整Live/查位/预约，不消耗完整Live环境重跑项；若后续要求完整Live，另行授权。

收益输出必须按两组逐家列出：每个词及来源、首屏认证店是否出现、打开的详情及累计名额、正确/未接纳/错认/环境失败，第三词是否实际贡献，调用数和等待时间。错认目标0，环境失败不进未接纳分母；不预先保证找回8家。历史冻结数据与新鲜响应受时间影响，只作限定比较；同批成对比较仅限已实际采集的共同原文，缺少另一策略需要的详情则标未评，不追加未授权GET，不用两个时代的均值冒充因果改善。
