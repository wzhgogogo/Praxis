## 关键发现：C3 在真实网站上几乎从不"稳定"

| 运行 | 判为仍在加载 | 稳定 | 等待合计 | 占运行时长 |
| --- | ---: | ---: | ---: | ---: |
| kf-h001 | 25 | 8 | 109 秒 | 43% |
| kf-h002 | 17 | 8 | 77 秒 | 35% |
| kf-h005 | 45 | 14 | 188 秒 | 51% |

- **TableCheck 页面一次都没有判为稳定**（kf-h005 共 0/26 次）。搜索框下的"Our diners also searched for…"建议文字会自动轮换（#37 与 #40 的可见文字不同），"可见内容不变"达不到；是否还有持续的请求，现有诊断没有记录，无法确认。
- 导航后的等待几乎都打满 4 秒（诊断里 URL 记为空，是直接导航后的等待）。
- 后果有三：完成判定被 PENDING 拦下（kf-h005 TableCheck 发现结果作废）；模型被提示"仍在加载"而多花 WAIT 调用（kf-h001 #4、#16、#24，kf-h002 #5、#8 等）；单店时限被等待吃掉，查位以 BROWSER_TIMEOUT 结束。
- 根因在我上一批写的规格："整页无未完成请求、整页可见内容不变"对真实页面太严格。应改成：只看与页面数据有关的请求（document、xhr、fetch），忽略图片、字体、媒体、信标和存在过久的长连接；超时后若两次快照中完成判定得出的**同一绑定结果**一致，就不应再因 PENDING 拒绝。

## 其他发现

1. **评估器与 C0c 的结束范围定义不一致。** C0c 把 `investigatedCandidateIds` 改为"实际查过的门店"（6 家），而 `unresolvedCandidateIds` 仍是全部 33 家；evaluator@26 仍按旧定义要求两者一致，于是判 COMPLETION_OUTCOME 为 NOT_SATISFIED。结束本身是诚实的，这是评测侧需要升版（@27）的问题。
2. **Tabelog 日历里没有的日期。** Tabelog 只把可订日期渲染成按钮；请求日期不可订时根本不出现在目标里，执行器还允许对其他日期按钮做普通 CLICK。模型因此去点别的日期（kf-h002 #9–16，8 次）。
3. **Agent 选店不看类型。** Agent 上下文里候选只有店名、地址，没有来源给出的类型或类别；kf-h005 按列表顺序先查了与 HARD 条件明显不符的店。
4. **Recorder 样式表仍为 0。** Tabelog 的样式表来自 `tblg.k-img.com`，走的是 ADR-0036 的通用公开 GET 规则，不在"已复核静态资源"里，所以没有存下。
5. **检索词：** "local food"在 Tabelog 与 TableCheck 再次 0 结果或无关结果；与 kf-h001 #24–28 是同一问题，已三次出现。

## 建议的下一批

1. **C3b（必须，先做）：** 请求条件只看 document/xhr/fetch，忽略静态资源、信标和存在超过约 3 秒的长连接；超时后用"两次快照的完成判定结果一致"代替整页稳定；诊断记录每次超时是哪个条件没满足（按资源类型的未完成请求数、命中的忙碌标记、可见文字是否在变）并记录真实 URL。用只读页面加载探测（不调模型）在 Tabelog 详情页、TableCheck 搜索页和店铺页上验证。
2. **E2 评估器 @27：** 按 C0c 的结束范围重新定义一致性检查：已查 ⊆ 已发现；每个已发现门店要么在已查中给出原因，要么列为未查。
3. **C2a 日历观察：** 请求日期在日历中存在但不可订时，作为"不可用"目标暴露并说明原因；查位阶段不再对非请求日期提供普通 CLICK。
4. **C8 Agent 选店：** 把来源已给出的类型或类别放进 Agent 上下文，Prompt 要求优先查与 HARD 条件一致的候选；用 kf-h005 #15、#28 的 Agent 决策回放验证。
5. **Recorder：** 通用公开规则放行的 CSS 也保存。
6. 之后再决定 kf-h005 是否用 1 次 Live 复测。
